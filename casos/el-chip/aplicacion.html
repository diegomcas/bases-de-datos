Cómo se ve El Chip desde un programa que la usa de verdad

Hasta acá la base fue algo que se consulta desde el Workbench. Pero una base de datos no existe sola: existe porque una aplicación la usa. Acá hay dos formas de verla funcionando, de menor a mayor.

Primero
Un script de consola

Doscientas líneas de Python. Se entiende entero de una sentada y muestra el ABM completo: alta, baja, modificación y consulta.

Después
Una aplicación web

El mismo caso resuelto como se haría en un trabajo real: Django, roles, reportes, tests y control de stock.

01

El script de consola

Lo mínimo para tocar la base desde un programa

Es un solo archivo, abm_elchip.py, que se conecta a MySQL y ofrece un menú de texto. No tiene framework ni dependencias raras: sirve para ver, sin distracciones, que una consulta SQL y una llamada desde Python son la misma cosa.

Tener la base cargada

Si todavía no lo hiciste, corré los scripts del caso en este orden. Sin esto, el programa se conecta pero no encuentra las tablas.

MySQL
SOURCE ElChip.sql;
SOURCE poblar_elchip.sql;

Instalar el conector

Es la biblioteca que traduce entre Python y MySQL.

Consola
pip install mysql-connector-python

Pasar la contraseña por el entorno

El programa la busca en una variable de entorno. Si no la encuentra, te la pide al arrancar. Nunca la escribas dentro del archivo: lo que entra a un repositorio queda en el historial para siempre.

PowerShell
$env:ELCHIP_DB_PASS = "tu_clave"

Ejecutarlo

Consola
python abm_elchip.py

Aparece el menú. Cada opción que elegís termina siendo un SELECT, un INSERT, un UPDATE o un DELETE de los que venimos escribiendo a mano.

⚠️ Si falla la conexión: revisá que el servicio de MySQL esté corriendo y que el usuario y la base coincidan con los del entorno (ELCHIP_DB_USER, ELCHIP_DB_NAME). El error que devuelve el conector dice bastante: leelo antes de tocar nada.

El archivo

abm_elchip.py Base SQLite de ejemplo
02

La aplicación web completa

El mismo caso, resuelto como en un trabajo real

Es un sistema de gestión hecho con Django sobre el modelo de El Chip: clientes con deduplicación, equipos, órdenes con máquina de estados, stock por movimientos trazables, cobros y cinco reportes de gestión. Se desarrolló en paralelo a la materia y sirve para ver adónde llega el modelo que diseñamos en la Unidad II cuando se lo lleva hasta el final.

Qué mirar cuando lo abras

  • Las tablas son las del DER. Cliente, equipo, orden, repuesto, pago: las mismas que modelaste, con los mismos nombres.
  • Los roles se aplican de verdad. Martín ve los reportes económicos; Sofía, la empleada, no. Es el requisito de seguridad del relato original, funcionando.
  • El stock no se edita, se mueve. Cada alta y cada baja deja un movimiento. Así se puede auditar por qué el stock dice lo que dice, que era el otro problema que Martín planteaba.
  • Los precios se congelan. Una orden vieja conserva el precio del día en que se hizo, no el actual.

Cómo se construyó

El sistema se desarrolló con asistencia de una IA, partiendo de la entrevista a Martín y del modelo ElChip.sql. La corrida quedó reconstruida escena por escena: los prompts reales, las cuatro rondas en que la IA frenó para preguntar, los tres huecos que encontró en el modelo entregado y los dos bugs que aparecieron recién al ejecutar.

La corrida, escena por escena

Ponerlo a andar

Hay dos caminos. El de SQLite no necesita instalar nada más y alcanza para recorrer el sistema; el de MySQL con Docker es la configuración de referencia.

Preparar el entorno

Consola
cp .env.example .env
python -m venv .venv
.venv\Scripts\pip install -r requirements-dev.txt

En Linux o Mac, el último comando es .venv/bin/pip install -r requirements-dev.txt.

Elegir la base

Camino corto, sin Docker: en el archivo .env dejá estas dos líneas activas y saltá el paso siguiente.

.env
DB_ENGINE=django.db.backends.sqlite3
DB_NAME=el_chip.sqlite3

Camino de referencia, con MySQL: dejá la configuración por defecto y levantá el contenedor.

Consola
docker compose up -d

Crear las tablas y cargar datos

Consola
python manage.py migrate
python manage.py cargar_datos_iniciales --demo

El --demo agrega datos de prueba y los dos usuarios. Sin esa opción sólo carga los catálogos, que es lo que se haría en producción.

Levantarlo

Consola
python manage.py runserver

Y abrir http://127.0.0.1:8000/

Cómo está organizado

Estructura
config/       proyecto Django: configuración y rutas
core/         utilidades comunes y comandos de mantenimiento
usuarios/     empleados y roles
catalogos/    tablas maestras: marcas, tipos, estados, métodos de pago
clientes/     clientes y sus contactos, con deduplicación
equipos/      equipos, apropiación y venta de abandonados
inventario/   repuestos, stock y movimientos
ordenes/      órdenes, líneas, consumos, pagos y máquina de estados
reportes/     los cinco informes de gestión
templates/    HTML con HTMX, sin compilación de JavaScript

La lógica de negocio vive en los services.py (lo que escribe) y selectors.py (lo que lee) de cada módulo. Las vistas son finas: ninguna toca un modelo directamente. Es una separación que vale la pena mirar aunque no sepas Django.

Dónde vive el código: el proyecto tiene su propio repositorio, aparte del de la materia, porque sigue su propio ritmo de cambios. El README de ahí tiene la versión corta de estas instrucciones y la lista completa de comandos de mantenimiento.
