01

Dos listas que no coinciden

Una consulta se escribe empezando por SELECT y termina en LIMIT. El motor la resuelve en otro orden: primero arma el conjunto de filas del que va a salir todo, y recién al final decide qué columnas mostrar y cómo ordenarlas.

Cómo se escribe

  1. SELECT
  2. FROM
  3. JOIN … ON
  4. WHERE
  5. GROUP BY
  6. HAVING
  7. ORDER BY
  8. LIMIT

Cómo se resuelve

  1. FROM de dónde salen las filas
  2. JOIN … ON se suman las otras tablas
  3. WHERE se descartan filas
  4. GROUP BY las filas se reparten en grupos
  5. se calculan los agregados
  6. HAVING se descartan grupos
  7. SELECT se arman las columnas de salida
  8. DISTINCT se sacan las repetidas
  9. ORDER BY se ordena el resultado
  10. LIMIT se corta

La lista de la derecha vale igual para las consultas que cruzan tablas con una coma, sin JOIN. Ahí desaparece la etapa 2 y el cruce entero ocurre en el FROM, que produce todas las combinaciones posibles; la condición que empareja las filas baja al WHERE, junto con los filtros. El resto del recorrido es el mismo.

Casi todo lo que sorprende de SQL sale de la distancia entre estas dos listas: por qué un alias funciona en ORDER BY y falla en WHERE, por qué la misma condición da resultados distintos según esté en WHERE o en HAVING, por qué después de agrupar hay columnas que dejan de poder nombrarse. Las diez etapas de la derecha alcanzan para explicar todo eso.

02

La consulta, etapa por etapa

Dos consultas sobre El Chip, con el juego de datos ampliado (8 órdenes, 8 clientes). Piden lo mismo y devuelven lo mismo; se diferencian en cómo cruzan las tablas. La primera usa la coma en el FROM y pone la relación en el WHERE, como se escribía antes de SQL-92. La segunda usa JOIN … ON.

Avanzá por las etapas y mirá qué tiene el motor en la mano en cada momento. Con la coma, la primera etapa arranca en 64 filas; con el JOIN, en 8. Las dos terminan en la misma fila, con tres columnas que no existían al empezar.

Ninguna etapa vuelve atrás: lo que descarta el WHERE no lo puede recuperar el HAVING, y lo que el SELECT no proyectó ya no está para que lo ordene el ORDER BY. Las dos versiones se separan en las tres primeras etapas y desde el GROUP BY recorren lo mismo, porque llegan ahí con las mismas seis filas.

La versión con coma muestra el mecanismo con más crudeza: el FROM produce todas las combinaciones posibles y el WHERE se queda con las que sirven. Esa es la definición del cruce, y el JOIN … ON es la manera de escribirla separando en dos lugares las dos condiciones que la coma mezcla en uno solo.

03

Cuando falta la condición que relaciona

Con la coma, la condición que empareja las tablas y la que filtra viven juntas en el WHERE. Olvidar la primera no produce ningún error: la consulta corre y devuelve números.

SQL
-- Falta O.id_cliente = C.id_cliente
SELECT C.apellido, COUNT(*) AS ordenes, SUM(O.total) AS facturado
FROM orden_servicio O, cliente C
WHERE O.total > 0
GROUP BY C.apellido;

Sin la condición de relación, el WHERE solo descarta las órdenes en cero y quedan 48 filas: las 6 órdenes que facturaron, apareadas con los 8 clientes. Cada cliente termina emparejado con todas las órdenes del taller, así que a cada apellido se le atribuye la facturación completa. Marcos Ferreyra, que no tiene ninguna orden, aparece con seis.

Los apellidos Pérez y Rossi duplican todo porque los comparten dos clientes: sus grupos reúnen dos veces las mismas 6 filas. Ese 337.000 es el doble exacto de 168.500, que a su vez es todo lo que cobró el taller. Cuando un total da redondo y repetido en varias filas, la primera sospecha es una condición de relación que falta.

El JOIN resuelve esto por gramática: FROM orden_servicio O INNER JOIN cliente C sin ON es un error de sintaxis y la consulta no llega a correr. Es el motivo por el que conviene escribir los cruces con JOIN aunque el resultado sea idéntico y el motor arme el mismo plan.

04

Qué queda cuando el grupo reemplaza a la fila

La etapa del GROUP BY es la que más cambia el terreno. Antes de agrupar, el motor tiene filas: cada una con todas sus columnas. Después de agrupar tiene grupos, y de cada grupo solamente puede nombrar dos cosas.

  • Las columnas por las que agrupó. Valen para todo el grupo: si el grupo se armó por C.apellido, ese apellido es único adentro del grupo.
  • Los resultados de funciones de agregación. COUNT, SUM, AVG, MIN y MAX resumen el grupo entero en un valor.
SQL
-- Agrupa por apellido y pide también el nombre de pila
SELECT C.apellido, C.nombre, COUNT(*) AS ordenes
FROM orden_servicio O
INNER JOIN cliente C ON C.id_cliente = O.id_cliente
GROUP BY C.apellido;

La consulta falla, y el mensaje explica exactamente el problema:

MySQL
ERROR 1055 (42000): Expression #2 of SELECT list is not in GROUP BY
clause and contains nonaggregated column 'el_chip.C.nombre' which is
not functionally dependent on columns in GROUP BY clause; this is
incompatible with sql_mode=only_full_group_by

El grupo Rossi junta la orden de Diego Rossi y la de Sofía Rossi. Preguntar «¿cuál es el nombre de pila del grupo Rossi?» no tiene respuesta, y el motor lo dice en lugar de elegir uno. Hay dos salidas, y eligen cosas distintas:

SQL
-- (a) Agrupar más fino: un grupo por persona, no por apellido
SELECT C.apellido, C.nombre, COUNT(*) AS ordenes
FROM orden_servicio O
INNER JOIN cliente C ON C.id_cliente = O.id_cliente
GROUP BY C.id_cliente, C.apellido, C.nombre;

-- (b) Resumir el nombre con un agregado, si el apellido es lo que interesa
SELECT C.apellido, COUNT(DISTINCT C.id_cliente) AS personas,
       COUNT(*) AS ordenes
FROM orden_servicio O
INNER JOIN cliente C ON C.id_cliente = O.id_cliente
GROUP BY C.apellido;

Resultado de (b) sobre el juego ampliado

Las cuatro órdenes de «Pérez» son de dos personas distintas: Juan Pérez tiene tres y su homónimo, una. Agrupar por apellido responde una pregunta sobre apellidos. Si la pregunta era por cliente, el grupo tiene que armarse por id_cliente.

05

El alias que todavía no existe

El alias de una columna nace en la etapa 7, cuando corre el SELECT. Todo lo que se ejecuta antes trabaja sin él.

SQL
-- El WHERE corre en la etapa 3: con_descuento todavía no existe
SELECT nro_orden, total, ROUND(total * 0.9, 2) AS con_descuento
FROM orden_servicio
WHERE con_descuento > 20000;
-- ERROR 1054 (42S22): Unknown column 'con_descuento' in 'where clause'

-- El ORDER BY corre en la etapa 9: el alias ya está armado
SELECT nro_orden, total, ROUND(total * 0.9, 2) AS con_descuento
FROM orden_servicio
WHERE total > 0
ORDER BY con_descuento DESC;

La segunda consulta, sobre el juego ampliado

527000.0024300.00

Para filtrar por el valor calculado hay que repetir la expresión en el WHERE —WHERE ROUND(total * 0.9, 2) > 20000— o envolver la consulta en otra y filtrar afuera. El motor calcula dos veces; a cambio, la regla se sostiene sin excepciones.

Una excepción de MySQL. En HAVING, MySQL acepta el alias del SELECT aunque por orden de ejecución todavía no exista. Es una extensión propia: PostgreSQL, SQL Server y Oracle rechazan lo mismo. La consola del sitio corre sobre PostgreSQL, así que ahí conviene escribir el agregado completo —HAVING SUM(O.total) > 20000— que funciona en todos los motores.

06

La misma condición en dos lugares

WHERE corre antes de agrupar y decide qué filas entran a los grupos. HAVING corre después y decide qué grupos sobreviven. Cambiar una condición de lugar cambia la composición de los grupos, no solamente el largo de la lista final.

SQL
-- (a) La orden sin cobrar se descarta ANTES de agrupar
SELECT C.apellido, COUNT(*) AS ordenes, SUM(O.total) AS facturado
FROM orden_servicio O
INNER JOIN cliente C ON C.id_cliente = O.id_cliente
WHERE O.total > 0
GROUP BY C.apellido;

-- (b) Entran todas las órdenes y el filtro se aplica al grupo
SELECT C.apellido, COUNT(*) AS ordenes, SUM(O.total) AS facturado
FROM orden_servicio O
INNER JOIN cliente C ON C.id_cliente = O.id_cliente
GROUP BY C.apellido
HAVING SUM(O.total) > 0;

(a) con WHERE — 6 filas entran a los grupos

apellidoordenesfacturado
García260500.00
Pérez399000.00
Rossi19000.00

(b) con HAVING — entran las 8 y después se filtra

apellidoordenesfacturado
García260500.00
Pérez499000.00
Rossi29000.00

Las dos listas tienen los mismos tres apellidos y los mismos totales. La columna ordenes no coincide: en (b) el grupo Pérez cuenta cuatro órdenes y el grupo Rossi cuenta dos, porque las órdenes pendientes en cero entraron a los grupos y aportaron 0 a la suma sin desaparecer del COUNT. Ninguna de las dos está mal: (a) responde «cuánto facturó cada apellido, contando las órdenes que cobraron algo» y (b) responde «cuántas órdenes trajo cada apellido, de los que alguna vez pagaron».

Cómo se elige. Si la condición se puede decidir mirando una fila sola, va en el WHERE. Si necesita el grupo entero —un COUNT, una SUM, un promedio—, no puede ir en el WHERE: en la etapa 3 los grupos todavía no existen. Escribir WHERE COUNT(*) > 1 devuelve ERROR 1111 (HY000): Invalid use of group function.

Cuando las dos ubicaciones dan el mismo resultado, conviene el WHERE: descarta filas antes de armar los grupos, así que el motor agrupa menos. La diferencia no se nota con ocho órdenes y sí con medio millón, que es el terreno de la clase de optimización.

07

Qué cuenta cada COUNT

Los agregados se calculan en la etapa 5, sobre las filas que quedaron en cada grupo. Con un LEFT JOIN hay grupos que existen por una fila donde la tabla de la derecha no aportó nada, y ahí COUNT(*) y COUNT(columna) se separan.

SQL
SELECT C.apellido, C.nombre,
       COUNT(*)             AS con_asterisco,
       COUNT(O.nro_orden)   AS con_columna,
       SUM(O.total)         AS facturado
FROM cliente C
LEFT JOIN orden_servicio O ON O.id_cliente = C.id_cliente
GROUP BY C.id_cliente, C.apellido, C.nombre;

MartínezAna10NULL
RossiDiego110.00
PérezJuan110.00
RossiSofía119000.00
FerreyraMarcos10NULL
  • COUNT(*) cuenta filas del grupo. López, Martínez y Ferreyra no tienen ninguna orden, pero el LEFT JOIN les dejó una fila con las columnas de orden_servicio en NULL. Esa fila se cuenta igual: da 1.
  • COUNT(columna) ignora los NULL. Por eso da 0, que es la respuesta correcta a «¿cuántas órdenes tiene?».
  • SUM de un grupo sin valores da NULL, no 0. Para mostrar cero se envuelve: IFNULL(SUM(O.total), 0).

Las dos últimas columnas también distinguen dos ceros distintos: Ferreyra no tiene órdenes (NULL) y Diego Rossi tiene una orden pendiente que todavía no facturó nada (0.00).

08

DISTINCT trabaja sobre lo ya proyectado

DISTINCT corre en la etapa 8, después de que el SELECT armó las columnas. Compara filas de salida completas, no filas de las tablas.

SQL
-- Apellidos de clientes que trajeron equipos: 3 filas
SELECT DISTINCT C.apellido
FROM orden_servicio O
INNER JOIN cliente C ON C.id_cliente = O.id_cliente;

-- Con el nro_orden agregado: 8 filas, DISTINCT no saca nada
SELECT DISTINCT C.apellido, O.nro_orden
FROM orden_servicio O
INNER JOIN cliente C ON C.id_cliente = O.id_cliente;

La segunda consulta devuelve las ocho filas: el número de orden es distinto en cada una, así que ninguna fila de salida se repite. DISTINCT se aplica a la fila entera que quedó proyectada, y sumar una columna a la lista casi siempre lo vuelve inofensivo.

Del mismo orden sale otra regla: con DISTINCT, el ORDER BY solo puede nombrar columnas que estén en el SELECT. Ordenar por O.total una lista de apellidos únicos no tiene sentido —cada apellido quedó con varias filas detrás, con totales distintos— y el motor lo rechaza en lugar de elegir uno.

09

ORDER BY y LIMIT, al final de todo

ORDER BY es la anteúltima etapa. Sin GROUP BY ni DISTINCT puede ordenar por columnas que no están en el SELECT, porque las filas de origen siguen disponibles.

SQL
-- Ordena por total sin mostrarlo: válido
SELECT C.apellido, C.nombre
FROM orden_servicio O
INNER JOIN cliente C ON C.id_cliente = O.id_cliente
ORDER BY O.total DESC;

-- Después de agrupar, esa columna ya no existe
SELECT C.apellido, COUNT(*) AS ordenes
FROM orden_servicio O
INNER JOIN cliente C ON C.id_cliente = O.id_cliente
GROUP BY C.apellido
ORDER BY O.total DESC;   -- ERROR 1055

Después del GROUP BY, el ORDER BY ordena grupos y solo puede nombrar lo que el grupo conserva: las columnas agrupadas y los agregados. Para ordenar por el total hay que agregarlo —ORDER BY SUM(O.total) DESC— y ahí sí funciona.

LIMIT cierra la fila de etapas. Corta el resultado ya ordenado, lo que tiene dos consecuencias que conviene tener presentes:

  • Un «top 3» sin ORDER BY devuelve las tres filas que hayan quedado adelante. El motor no garantiza cuáles: con una tabla chica suelen salir por orden de inserción, y con una tabla grande, o después de un borrado, cambian sin aviso.
  • LIMIT no le ahorra trabajo al motor. Para saber cuáles son las tres primeras hay que resolver el JOIN, filtrar, agrupar y ordenar todo. Un LIMIT 3 sobre medio millón de filas ordena medio millón de filas.
10

Qué existe en cada etapa

La tabla resume lo que se puede nombrar en cada cláusula, y es la que conviene tener a mano cuando el motor devuelve un error de columna desconocida.

En esta cláusula Columnas de las tablas Funciones de agregación Alias del SELECT
ON (etapa 2) sí no no
WHERE (etapa 3) sí no no
GROUP BY (etapa 4) sí no en MySQL sí
HAVING (etapa 6) solo las agrupadas sí en MySQL sí
SELECT (etapa 7) solo las agrupadas sí no, se están creando
ORDER BY (etapa 9) solo las agrupadas sí sí

La columna «solo las agrupadas» vale cuando hay GROUP BY. Sin agrupación, esas tres cláusulas ven todas las columnas de las tablas del FROM.

Las tres excepciones de MySQL. MySQL acepta el alias del SELECT en GROUP BY y en HAVING, y con sql_mode sin ONLY_FULL_GROUP_BY deja proyectar columnas que no están en el grupo, eligiendo un valor cualquiera. Desde MySQL 5.7 ese modo viene activado, así que el error 1055 es lo esperable. Escribir la versión estricta funciona en cualquier motor y evita depender de una configuración.

11

El orden lógico y el plan real

Las diez etapas describen el significado de la consulta: el resultado tiene que ser el mismo que si el motor las ejecutara una tras otra, en ese orden. Lo que el motor hace adentro es otra cosa.

Ninguna base de datos arma de verdad el producto de las tablas para después descartar el 99 % con el WHERE. El optimizador reordena: empuja los filtros hacia abajo para que el JOIN trabaje con menos filas, elige por cuál tabla empezar, usa índices para saltear la lectura completa. Todo eso está permitido mientras el resultado no cambie.

SQL
-- Qué plan eligió el motor para esta consulta
EXPLAIN SELECT C.apellido, COUNT(*) AS ordenes
FROM orden_servicio O
INNER JOIN cliente C ON C.id_cliente = O.id_cliente
WHERE O.total > 0
GROUP BY C.apellido;

El orden lógico sirve para dos cosas distintas, y las dos hacen falta: predecir qué va a devolver una consulta y entender por qué un error aparece donde aparece. El plan de ejecución real, con EXPLAIN, es el tema de la clase de optimización, donde la pregunta pasa a ser cuánto tarda.

Para practicar. Abrí la consola con el juego de datos ampliado (opción 2 · Compendio) y corré las dos consultas del visor cortándolas por etapa, agregando una cláusula por vez. Con la coma las cuentas de filas tienen que darte 64, 8, 6 y 3 grupos; con el JOIN, 8, 8, 6 y 3. Para contar sin leer todo, envolvé cada paso en un SELECT COUNT(*) FROM ( … ) AS t.
