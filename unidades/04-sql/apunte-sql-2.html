Parte VI · Definir la base

Hasta acá la base venía dada: alguien había creado las tablas y nosotros escribíamos consultas. Esta parte es el otro lado, el que ya se había trabajado al modelar: convertir un diseño en tablas que existen de verdad.

26 · Los cinco sublenguajes

SQL no es un lenguaje uniforme: sus sentencias se agrupan en cinco conjuntos, según lo que hacen. La división sirve para ubicarse, y también para entender por qué algunas sentencias se pueden deshacer y otras no.

SiglaQué haceSentenciasDónde
DDL Definición: crea y modifica la estructura CREATE, ALTER, DROP, TRUNCATE §27 a §29
DML Manipulación: agrega, cambia y borra filas INSERT, UPDATE, DELETE §22 a §25
DQL Consulta: pregunta sin cambiar nada SELECT §1 a §21
DCL Control de datos: quién puede qué CREATE USER, GRANT, REVOKE §38 y §39
TCL Control de transacciones: confirmar o deshacer START TRANSACTION, COMMIT, ROLLBACK, SAVEPOINT §40 y §41

El DDL confirma solo, y eso no se puede deshacer

En MySQL, toda sentencia DDL provoca un commit implícito: cierra la transacción abierta y se confirma sola. Un CREATE TABLE o un DROP TABLE adentro de una transacción no se deshacen con ROLLBACK (§40).

Por eso el DML se puede ensayar y el DDL se piensa antes. DROP TABLE no tiene vuelta atrás.

27 · CREATE TABLE y los tipos de dato

Crear una tabla es declarar sus columnas, y cada columna necesita un tipo: qué clase de dato admite y cuánto espacio ocupa. El tipo es la primera regla de calidad del dato, porque impide de entrada lo que no tiene sentido.

CREATE TABLE [IF NOT EXISTS] nombre_tabla (
  columna_1 TIPO [restricciones],
  columna_2 TIPO [restricciones],
  [restricciones de tabla]);
TipoPara quéEn El Chip
INTNúmeros enteros: identificadores, cantidades.id_cliente, stock
DECIMAL(p,e)Números exactos con decimales: dinero. p son los dígitos totales y e los de la parte decimal.precio_unitario DECIMAL(10,2)
VARCHAR(n)Texto de largo variable, hasta n caracteres.apellido VARCHAR(100)
CHAR(n)Texto de largo fijo. Para códigos que siempre miden lo mismo.—
TEXTTexto largo, sin límite práctico. No admite valor por defecto.—
DATE / DATETIMEDía, o día y hora (§30).fecha_ingreso DATETIME
BOOLEANVerdadero o falso. En MySQL es un TINYINT(1): guarda 1 y 0.—

El error de siempre

Guardar dinero en FLOAT o DOUBLE. Esos tipos son aproximados: 0.1 + 0.2 no da exactamente 0.3, y en una suma de miles de operaciones la diferencia aparece. Para plata, siempre DECIMAL.

Y el opuesto: guardar números en VARCHAR. Un ORDER BY sobre texto ordena '10' antes que '9', porque compara carácter por carácter.

28 · Las restricciones

Una restricción es una regla que la base hace cumplir por su cuenta, sin depender de que el programa se acuerde. Es lo que vuelve confiable a los datos: lo que la restricción prohíbe, no puede entrar por ningún camino.

RestricciónQué garantiza
PRIMARY KEYIdentifica la fila. Es única y no admite nulos. El motor le crea un índice solo (§43).
AUTO_INCREMENTEl motor numera solo, y el contador no vuelve atrás (§22).
FOREIGN KEYEl valor tiene que existir en la tabla referenciada. Es la integridad referencial (§24).
NOT NULLLa columna no puede quedar sin dato.
UNIQUENo se repite el valor. A diferencia de la clave primaria, admite nulos.
DEFAULT valorSi el INSERT no la nombra, toma ese valor.
CHECK (condición)La fila solo entra si cumple la condición. MySQL la hace cumplir desde la versión 8.0.16.

Ejemplo · una tabla con todas sus reglas puestas

SQL
CREATE TABLE garantia (
    id_garantia  INT AUTO_INCREMENT,
    nro_orden    INT NOT NULL,
    dias         INT NOT NULL DEFAULT 90,
    observacion  VARCHAR(200) NULL,
    emitida      DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id_garantia),
    UNIQUE (nro_orden),
    CONSTRAINT fk_garantia_orden
        FOREIGN KEY (nro_orden) REFERENCES orden_servicio (nro_orden),
    CONSTRAINT ck_garantia_dias CHECK (dias > 0));

Una garantía por orden (UNIQUE), que no puede apuntar a una orden inexistente (FOREIGN KEY), con noventa días si nadie dice otra cosa (DEFAULT) y nunca con días negativos (CHECK).

Nombrar las restricciones

CONSTRAINT nombre le pone nombre a la regla. Sin eso el motor le inventa uno, y cuando la restricción salta, el mensaje de error no dice nada útil. Con nombre, el error trae ck_garantia_dias y se sabe al instante qué regla se violó.

29 · ALTER y DROP: cambiar lo que ya existe

Una base en uso cambia: aparece un dato que no se había previsto, una regla que hay que agregar, una tabla que dejó de servir. ALTER TABLE modifica la estructura sin perder los datos.

ALTER TABLE tabla ADD COLUMN columna TIPO [restricciones];
ALTER TABLE tabla MODIFY COLUMN columna TIPO_NUEVO;
ALTER TABLE tabla CHANGE COLUMN vieja nueva TIPO;
ALTER TABLE tabla DROP COLUMN columna;
ALTER TABLE tabla ADD CONSTRAINT nombre FOREIGN KEY (col) REFERENCES otra (col);
ALTER TABLE tabla DROP FOREIGN KEY nombre;

Agregar una columna NOT NULL a una tabla con datos

Si la tabla ya tiene filas, la columna nueva necesita un DEFAULT: si no, las filas existentes quedarían con un nulo que la restricción prohíbe, y el ALTER falla. La otra salida es en tres pasos: agregarla nula, completarla con un UPDATE (§23) y recién entonces marcarla NOT NULL.

Para eliminar hay tres sentencias que se confunden seguido y hacen cosas muy distintas:

SentenciaQué borra¿Se deshace?
DELETE FROM t WHERE …Las filas que cumplen la condición. Sin WHERE, todas.Sí, con ROLLBACK (es DML).
TRUNCATE TABLE tTodas las filas de un saque, y reinicia el AUTO_INCREMENT.No: es DDL.
DROP TABLE tLa tabla entera: filas, estructura, índices y permisos.No: es DDL.

El error de siempre

Confundir TRUNCATE con DELETE porque «hacen lo mismo». TRUNCATE es más rápido y deja la tabla como recién creada, pero no se puede deshacer, no dispara los triggers (§37) y el motor lo rechaza si alguna clave foránea apunta a esa tabla.

Parte VII · Fechas y horas

Las fechas parecen texto y no lo son. Tienen su tipo, su aritmética y una forma de compararse que se lleva mal con la intuición. Casi todo reporte que se pide en un trabajo real tiene una fecha adentro.

30 · Cómo se guarda una fecha

  • DATE guarda solo el día: 2026-05-22.
  • DATETIME guarda el día y la hora: 2026-05-22 11:05:00.

MySQL escribe y lee las fechas siempre en el mismo orden, del año al segundo: 'AAAA-MM-DD hh:mm:ss'. Ese formato no depende del país ni de la configuración; el formato argentino aparece recién al mostrar (§31).

En El Chip, fecha_ingreso, fecha_entrega y fecha_pago son DATETIME. Que guarden la hora es lo que hace interesante —y traicionero— el filtrado de §32.

La fecha de hoy

CURDATE() devuelve el día de hoy y NOW(), el día y la hora. Una consulta que las usa devuelve algo distinto cada vez que se ejecuta, así que no sirve para comparar resultados entre dos días ni para un examen: por eso los ejemplos de acá usan fechas escritas.

31 · Leer una fecha: sacarle partes y mostrarla

De un DATETIME se pueden extraer pedazos, y cada función devuelve un número:

DATE(f) TIME(f)       — separan el día y la hora
YEAR(f) MONTH(f) DAY(f)  — el número de año, mes y día
HOUR(f) MINUTE(f)      — la hora y los minutos

Ejemplo · las órdenes que entraron por la mañana

SQL
SELECT nro_orden,
       DATE(fecha_ingreso) AS dia,
       HOUR(fecha_ingreso) AS hora
FROM orden_servicio
WHERE HOUR(fecha_ingreso) < 12
ORDER BY nro_orden;

Ordenar por la fecha ya formateada. DATE_FORMAT devuelve texto, y el texto se ordena carácter por carácter: '02/01/2027' va antes que '15/05/2026', porque el 0 es menor que el 1. El ORDER BY tiene que ir sobre la columna original, que se ordena como fecha, y el formato queda solo para mostrar.

32 · Filtrar por fechas

Las fechas se comparan con los operadores de siempre contra un literal entre comillas: fecha_ingreso >= '2026-05-15'. Lo que hay que tener presente es qué pasa con la hora.

Si el literal no trae hora, MySQL le pone 00:00:00

'2026-05-22' equivale a '2026-05-22 00:00:00', que es el primer instante del día. Por eso un BETWEEN '2026-05-15' AND '2026-05-22' sobre una columna DATETIME deja afuera casi todo el día 22: solo entra lo que haya ocurrido exactamente a la medianoche.

Ejemplo · el rango que se come el último día

SQL
SELECT nro_orden, fecha_ingreso
FROM orden_servicio
WHERE fecha_ingreso BETWEEN '2026-05-01' AND '2026-05-10'
ORDER BY nro_orden;
nro_ordenfecha_ingreso

22026-05-02 11:30:00

2 filas

La orden 3 entró el 10 de mayo a las 10:45 y no aparece: el rango termina el 10 a las 00:00.

Ejemplo · la forma que sí incluye el último día

SQL
SELECT nro_orden, fecha_ingreso
FROM orden_servicio
WHERE fecha_ingreso >= '2026-05-01'
  AND fecha_ingreso <  '2026-05-11'

El límite de arriba es el día siguiente, con < estricto. Ahora sí entra el 10 completo, hasta las 23:59:59.

La forma recomendada para cualquier rango de fechas

columna >= inicio AND columna < día_siguiente_al_final. Además de incluir el último día entero, es la forma que permite al motor usar el índice, cosa que DATE(columna) = '…' impide (§44).

33 · Calcular con fechas

FunciónQué devuelve
DATEDIFF(fin, inicio) Días de calendario entre las dos fechas. Ignora la hora.
TIMESTAMPDIFF(unidad, inicio, fin) Cuántas unidades completas pasaron: MINUTE, HOUR, DAY, MONTH, YEAR.
DATE_ADD(f, INTERVAL n unidad)
DATE_SUB(f, INTERVAL n unidad)		 La fecha corrida hacia adelante o hacia atrás.

Las dos funciones de diferencia llevan los argumentos al revés

DATEDIFF(fin, inicio) empieza por el final; TIMESTAMPDIFF(unidad, inicio, fin) empieza por el principio. Invertirlos no da error: da el número en negativo, que pasa desapercibido en un promedio.

Ejemplo · dos horas de diferencia, un día de diferencia

SQL
SELECT DATEDIFF('2026-05-02 01:00', '2026-05-01 23:00')             AS datediff_dias,
       TIMESTAMPDIFF(DAY,  '2026-05-01 23:00', '2026-05-02 01:00') AS timestampdiff_dias,
       TIMESTAMPDIFF(HOUR, '2026-05-01 23:00', '2026-05-02 01:00') AS horas;

34 · De texto a fecha

STR_TO_DATE(texto, patrón) hace el camino inverso a DATE_FORMAT: lee un texto según el patrón y devuelve una fecha de verdad, con la que ya se puede comparar y calcular. Los símbolos del patrón son los mismos de §31.

Hace falta cada vez que un dato llega escrito por una persona: una planilla, un cuaderno, un formulario viejo. Y el patrón es lo que decide qué número es el día y cuál el mes.

Ejemplo · el mismo texto, dos fechas distintas

SQL
SELECT STR_TO_DATE('10/03/2026 15:30', '%d/%m/%Y %H:%i') AS argentino,
       STR_TO_DATE('10/03/2026 15:30', '%m/%d/%Y %H:%i') AS estadounidense;
argentinoestadounidense
2026-03-10 15:30:002026-10-03 15:30:00

1 fila

El mismo texto es el 10 de marzo o el 3 de octubre según el patrón. Ninguna de las dos lecturas da error: las dos son fechas válidas.

El error de siempre

Suponer el formato de un archivo que vino de otro lado. Si el patrón no coincide, MySQL devuelve NULL y una advertencia —no un error—, así que la fila se carga con la fecha vacía y nadie se entera hasta que el reporte sale mal. Conviene probar primero con un SELECT sobre un puñado de filas.

Parte VIII · Cuando la base reacciona sola

Todo lo anterior son órdenes que alguien escribe y el motor obedece. Lo que sigue queda guardado adentro de la base y actúa después: una consulta con nombre, un procedimiento que se llama, un disparador que se activa solo.

35 · Vistas

Una vista es una consulta guardada con un nombre. No duplica los datos ni ocupa espacio: cada vez que alguien la consulta, el motor ejecuta por debajo el SELECT que la define. Desde afuera se usa igual que una tabla.

CREATE [OR REPLACE] VIEW nombre AS
  SELECT …;

DROP VIEW [IF EXISTS] nombre;

Sirve para tres cosas distintas: guardar de una vez una consulta con uniones complicadas, presentar los datos con los nombres que entiende quien los lee, y mostrar solo una parte de la tabla (§39).

Ejemplo · la consulta del mostrador, guardada

SQL
CREATE VIEW orden_para_mostrador AS
SELECT O.nro_orden,
       C.apellido,
       O.fecha_ingreso,
       E.nombre AS estado
FROM orden_servicio O
INNER JOIN cliente C      ON C.id_cliente = O.id_cliente
INNER JOIN orden_estado E ON E.id_orden_estado = O.id_orden_estado;

SELECT * FROM orden_para_mostrador ORDER BY nro_orden;
nro_ordenapellidofecha_ingresoestado
1Pérez2026-05-01 10:00:00Entregado

Quien atiende el mostrador escribe SELECT * FROM orden_para_mostrador y no necesita saber que abajo hay dos uniones.

La vista siempre muestra los datos de ahora

No es una foto: es la consulta. Si entra una orden nueva, la vista la muestra en la próxima consulta sin que nadie la actualice. Y si cambia la estructura de las tablas de abajo, la vista puede romperse: quedan apuntando a una columna que ya no existe.

CREATE OR REPLACE VIEW la redefine sin tener que borrarla primero.

Lo que una vista no puede hacer

Una vista con GROUP BY, DISTINCT o uniones no admite INSERT ni UPDATE: el motor no sabría a qué fila original corresponde cada fila del resumen. Las vistas simples —un SELECT de columnas de una sola tabla— sí son actualizables, pero conviene tratarlas como de solo lectura y escribir siempre sobre las tablas.

36 · Procedimientos almacenados

Un procedimiento es un bloque de sentencias guardado en el servidor con un nombre, que recibe parámetros y se ejecuta con CALL. En lugar de que cada persona escriba el UPDATE completo —y se olvide el WHERE—, llama al procedimiento y le pasa los datos.

DELIMITER //
CREATE PROCEDURE nombre(IN parametro TIPO, OUT resultado TIPO)
BEGIN
  sentencias;
END //
DELIMITER ;

CALL nombre(valor, @variable);

Para qué es el DELIMITER

El cliente de MySQL corta las sentencias en cada ;, y el cuerpo del procedimiento está lleno de ;. DELIMITER // le dice «de acá en adelante, una sentencia termina con //», y así el CREATE PROCEDURE entero le llega al servidor de una pieza. Al terminar se vuelve a ;.

Es una instrucción del cliente, no del servidor: en una herramienta gráfica puede no hacer falta, y en la consola del sitio no existe.

Los parámetros llevan una marca según para qué lado va el dato: IN entra, OUT sale, INOUT hace las dos cosas.

Ejemplo · cambiar un precio sin escribir el UPDATE

SQL
DELIMITER //
CREATE PROCEDURE cambiar_precio_repuesto(
    IN p_id_repuesto INT,
    IN p_nuevo_precio DECIMAL(10,2))
BEGIN
    UPDATE repuesto
    SET precio_unitario = p_nuevo_precio
    WHERE id_repuesto = p_id_repuesto;
END //
DELIMITER ;

CALL cambiar_precio_repuesto(1, 48000.00);

SELECT id_repuesto, nombre, precio_unitario
FROM repuesto
WHERE id_repuesto = 1;
id_repuestonombreprecio_unitario
1Módulo Samsung S21 Original48000.00

1 fila

El módulo de Samsung valía 45000.00. Quien atiende no escribió ningún UPDATE: pasó el id y el precio nuevo.

Qué se gana

La regla queda escrita en un solo lugar, el WHERE no se puede olvidar, y se puede dar permiso para ejecutar el procedimiento sin dar permiso para modificar la tabla (§38). Además el motor lo tiene ya preparado, sin analizarlo de nuevo en cada llamada.

37 · Disparadores

Un disparador —trigger— es un bloque de código que el motor ejecuta solo cuando ocurre algo en una tabla. Nadie lo llama: se declara una vez y queda activo. Es un sensor de movimiento, no un interruptor.

CREATE TRIGGER nombre
{BEFORE | AFTER} {INSERT | UPDATE | DELETE} ON tabla
FOR EACH ROW
BEGIN
  sentencias;
END

Adentro del cuerpo hay dos palabras que dan acceso a la fila involucrada:

  • NEW.columna — el valor que se está por guardar. Existe en INSERT y en UPDATE.
  • OLD.columna — el valor que había antes. Existe en UPDATE y en DELETE.

Un disparador BEFORE corre antes de escribir, así que puede revisar o corregir el dato; uno AFTER corre después, y sirve para registrar lo que pasó en otra tabla.

Ejemplo · impedir que el stock quede en negativo

SQL
DELIMITER //
CREATE TRIGGER trg_control_stock_negativo
BEFORE UPDATE ON repuesto
FOR EACH ROW
BEGIN
    IF NEW.stock < 0 THEN
        SIGNAL SQLSTATE '45000'
        SET MESSAGE_TEXT = 'No se puede dejar el stock en negativo.';
    END IF;
END //
DELIMITER ;

-- Con el disparador puesto, esto ya no entra:
UPDATE repuesto SET stock = -5 WHERE id_repuesto = 1;
-- ERROR 1644 (45000): No se puede dejar el stock en negativo.

SIGNAL SQLSTATE '45000' es la forma de que un disparador cancele la operación con un mensaje propio. El error llega como 1644, que es el código de los errores definidos por quien programó la base.

Por qué conviene usarlos con medida

Un disparador es código que corre sin que nadie lo vea en la consulta. Cuando un UPDATE de una línea hace cosas que no están escritas ahí, depurar se vuelve difícil: hay que acordarse de ir a buscar qué disparadores tiene esa tabla.

Por eso, para una regla simple sobre una columna conviene primero un CHECK (§28), que dice lo mismo y queda a la vista en la definición de la tabla. El disparador se justifica cuando hay que tocar otra tabla: llevar un registro de cambios, mantener un total acumulado.

Y recordá que TRUNCATE no los dispara (§29).

Parte IX · Quién puede qué, y el todo o nada

Los dos sublenguajes que faltaban. Uno decide quién entra y hasta dónde; el otro, qué pasa cuando una operación son varias sentencias y no pueden quedar hechas a medias.

38 · Permisos: el DCL

El DCL tiene tres verbos: CREATE USER crea a quien se conecta, GRANT le da permisos y REVOKE se los quita. El permiso se otorga por operación y por objeto, y lo que no se otorga no se puede.

CREATE USER 'nombre'@'localhost' IDENTIFIED BY 'clave';
GRANT SELECT, INSERT ON esquema.tabla TO 'nombre'@'localhost';
REVOKE INSERT ON esquema.tabla FROM 'nombre'@'localhost';
SHOW GRANTS FOR 'nombre'@'localhost';

Un usuario de la base no es un empleado

La tabla empleado de El Chip guarda a quién contrató Martín: son datos. El usuario de MySQL es quién puede conectarse al servidor: es una cuenta del motor. Son dos cosas distintas y conviene no mezclarlas, aunque a veces se correspondan.

El 'localhost' del final forma parte del nombre: 'sofia'@'localhost' y 'sofia'@'%' son dos usuarios diferentes, y el segundo puede conectarse desde cualquier máquina.

Ejemplo · darle a alguien lo mínimo que necesita

SQL
CREATE USER 'sofia'@'localhost' IDENTIFIED BY 'una_clave_larga';

GRANT SELECT, INSERT ON el_chip.orden_servicio TO 'sofia'@'localhost';
GRANT SELECT         ON el_chip.cliente        TO 'sofia'@'localhost';

SHOW GRANTS FOR 'sofia'@'localhost';

Sofía puede leer los clientes y cargar órdenes. No puede ver empleado, ni cambiar un precio, ni borrar nada: para el motor, esas operaciones no existen para ella.

El principio de mínimo privilegio

Se otorga lo que hace falta para trabajar, y nada más. No porque se desconfíe de la persona: porque una cuenta con permisos de más convierte cualquier error —o cualquier contraseña filtrada— en un problema mucho más grande.

Eso es lo que hace un DBA: decide quién ve qué, y lo escribe en SQL.

39 · La vista como frontera

GRANT SELECT se da sobre la tabla completa. Si alguien necesita ver el número y el estado de las órdenes pero no los montos, el permiso por tabla no alcanza: o ve todo, o no ve nada.

La salida es una vista (§35). Se crea mostrando solo lo que corresponde, y el permiso se otorga sobre la vista en lugar de sobre las tablas:

Ejemplo · el permiso apoyado en una vista

SQL
-- La vista recorta: nro_orden, apellido, fecha y estado. El total no está.
REVOKE SELECT ON el_chip.orden_servicio       FROM 'sofia'@'localhost';
GRANT  SELECT ON el_chip.orden_para_mostrador TO   'sofia'@'localhost';

Sofía consulta la vista sin tener permiso sobre ninguna de las tablas que la componen.

Por qué funciona

Una vista se ejecuta con los permisos de quien la creó, no de quien la consulta. Por eso alcanza con darle acceso a la vista: el motor lee las tablas de abajo por cuenta del creador.

Es el mismo objeto de §35 con otro uso. Allá la vista servía para no repetir una consulta complicada; acá dibuja una frontera.

A practicar Taller: permisos y transacciones, bloques 1 y 2.

40 · Transacciones: el todo o nada

Una transacción es un bloque de sentencias que el motor trata como una sola. Se abre con START TRANSACTION y se cierra de dos maneras: COMMIT confirma todo, ROLLBACK deshace todo.

START TRANSACTION;
  sentencias;
  SAVEPOINT nombre;
  ROLLBACK TO nombre;
COMMIT;  — o ROLLBACK;

Hace falta cada vez que una operación del negocio son varias sentencias. Dar de alta un cliente con su teléfono son dos INSERT, y un cliente cargado sin teléfono porque el segundo falló es peor que no haberlo cargado.

El modo automático

Por omisión, MySQL confirma cada sentencia apenas se ejecuta: cada UPDATE es su propia transacción, ya cerrada. START TRANSACTION suspende ese comportamiento hasta el COMMIT.

Hasta ese COMMIT, nadie más ve los cambios: quien consulte desde otra conexión sigue viendo los datos viejos.

Ejemplo · deshacer una parte sin abandonar el resto

SQL
INSERT INTO cliente (nombre, apellido) VALUES ('Laura', 'Fernández');

SAVEPOINT alta_laura;

INSERT INTO cliente (nombre, apellido) VALUES ('ERROR', 'ERROR');

ROLLBACK TO alta_laura;

SELECT id_cliente, nombre, apellido
FROM cliente
ORDER BY id_cliente DESC
LIMIT 3;
id_clientenombreapellido
6LauraFernández
5DiegoRossi
4AnaMartínez

3 filas

Laura quedó cargada y la fila errónea no. El SAVEPOINT marca un punto intermedio al que se puede volver sin tirar abajo toda la transacción.

Lo que el ROLLBACK no deshace

El contador de AUTO_INCREMENT (§22): los números que consumió una transacción deshecha quedan consumidos. Es a propósito, para que dos sesiones simultáneas nunca reciban el mismo id.

Las sentencias DDL (§26): un CREATE, un ALTER o un DROP confirman solos y cierran la transacción abierta.

41 · Las cuatro letras de ACID

ACID nombra las cuatro garantías que da una transacción. Son cuatro cosas que se pueden ver funcionando, no una sigla para repetir de memoria.

LetraQué garantizaCómo se ve
Atomicidad La transacción entra entera o no entra. Un ROLLBACK después de dos INSERT: no queda ninguno.
Consistencia Al terminar, la base cumple todas sus reglas: claves foráneas, NOT NULL, UNIQUE, CHECK. Una sentencia que violaría una restricción no se ejecuta, esté o no en una transacción.
Aislamiento Lo que hace una transacción no lo ve otra hasta el COMMIT. Hacen falta dos sesiones abiertas a la vez para comprobarlo.
Durabilidad Una vez confirmado, sobrevive a que se corte la luz. Es la única que no se puede demostrar en el aula sin desenchufar algo.

Parte X · Que ande rápido

Todo lo anterior da resultados correctos. Esta parte es sobre el tiempo que tardan en llegar, que con ocho órdenes no se nota y con medio millón de filas decide si el sistema sirve.

42 · Medir antes de opinar

La base de El Chip tiene ocho órdenes: cualquier consulta responde en 0,00 segundos, con índice o sin él. Sobre datos de juguete todas las consultas parecen buenas, y por eso el primer paso de cualquier trabajo de optimización es generar volumen.

El segundo paso es EXPLAIN, que no mide tiempo: muestra cómo piensa resolver el motor la consulta antes de ejecutarla. Sirve incluso cuando la tabla es chica, porque revela si va a recorrerla entera o a usar un índice.

Optimizar sin medir es adivinar

La intuición sobre qué es lento se equivoca seguido, y el motor a veces tiene razones que uno no ve. Antes de crear un índice: medir el tiempo, mirar el plan, cambiar una sola cosa y volver a medir.

En la consola del sitio, que corre PostgreSQL, el plan se pide igual con EXPLAIN pero se lee distinto: ahí donde MySQL dice type: ALL, PostgreSQL dice Seq Scan; y el uso de índice aparece como Index Scan.

43 · El índice

Un índice es una copia ordenada de una columna, con un puntero a la fila completa. Es el índice alfabético del libro: en vez de leer todas las páginas buscando una palabra, se va a la letra.

CREATE INDEX nombre ON tabla (columna);
CREATE INDEX nombre ON tabla (columna_a, columna_b);  — compuesto
DROP INDEX nombre ON tabla;
SHOW INDEX FROM tabla;

Una vez creado, el motor lo usa solo cuando le conviene: no hay que nombrarlo en la consulta. Sirve para buscar por igualdad o por rango, para ordenar y para unir por la clave foránea.

Ejemplo · el mismo plan, después del índice

CREATE INDEX ix_cliente_apellido ON cliente (apellido);

La clave primaria ya tiene índice

El motor lo crea solo al declararla. Por eso buscar por id_cliente siempre fue rápido sin que nadie hiciera nada. Las claves foráneas, en MySQL con InnoDB, también reciben uno automáticamente.

44 · Cuando el índice no sirve

Crear un índice no garantiza que se use. Hay cuatro situaciones que conviene reconocer, porque explican la mayoría de los casos en que «el índice no hizo nada».

Una función sobre la columna lo anula

El índice guarda fecha_ingreso, no YEAR(fecha_ingreso). Si la consulta pregunta por el resultado de una función, el motor no puede buscarlo en el índice y recorre la tabla entera.

Por eso WHERE fecha >= '2026-05-01' AND fecha < '2026-06-01' puede usar el índice y WHERE MONTH(fecha) = 5 no. Es la misma pregunta escrita de dos maneras, y es el motivo de la forma recomendada de §32.

  • Un LIKE que empieza con comodín. 'Mov%' se puede buscar en un índice ordenado, porque se sabe por dónde empezar; '%999%' no.
  • Cada índice hace más lenta la escritura. Todo INSERT, UPDATE y DELETE tiene que actualizar también los índices de esa tabla. Un índice que nadie usa solo cuesta.
  • El motor puede decidir ignorarlo. Si estima que recorrer la tabla entera sale más barato que ir y volver del índice, lo hace, y casi siempre tiene razón. Pasa cuando la consulta va a devolver buena parte de la tabla.

45 · Qué indexar

CandidatasPor qué
Las claves foráneas Son las columnas por las que se unen las tablas. Una unión sin índice del lado «muchos» es lo primero que se pone lento cuando la base crece.
Las columnas por las que se busca seguido Un número de documento, un número de serie, una fecha de ingreso.
Las que se usan para ordenar listados grandes El índice ya está ordenado: el motor se ahorra ordenar.
Casi nunca: estados, tipos, banderas de sí o no Son de baja selectividad: con cuatro estados posibles, buscar uno devuelve la cuarta parte de la tabla y recorrerla entera sale más barato.

El índice compuesto y el orden de sus columnas

CREATE INDEX ix ON t (a, b) sirve para buscar por a, y para buscar por a y b juntas. No sirve para buscar solo por b: es una guía telefónica ordenada por apellido y nombre, que no ayuda a encontrar a todos los «Martín».

La columna más selectiva —la que más descarta— va primero.
