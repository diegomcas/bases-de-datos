01

Subconsultas Escalares - Resoluciones

Comparar registros individuales contra un único resultado dinámico

Consejo de trabajo

Ejecutá primero la consulta interna sola —SELECT AVG(precio_unitario) FROM repuesto— y anotá el número que devuelve. Después mirá la consulta completa: la externa reemplaza esa fórmula por ese valor cada vez que se ejecuta, así que si mañana cambian los precios el resultado cambia solo.

  • Reto 1.1

    Repuestos con precio mayor que el promedio

    Volver a la consigna
    SQL 
    SELECT nombre, precio_unitario 
FROM repuesto 
WHERE precio_unitario > (
    SELECT AVG(precio_unitario) 
    FROM repuesto
);

    Explicación: La subconsulta escalar calcula el promedio de la tabla. Al devolver un único valor flotante, el operador > funciona perfectamente. Si agregáramos una columna extra dentro de los paréntesis (por ejemplo, SELECT nombre, AVG(...)), MySQL daría error de sintaxis porque dejaría de ser escalar.

  • Reto 1.2

    Marca del equipo de la orden 1 (Anidamiento múltiple)

    Volver a la consigna
    SQL 
    SELECT nombre 
FROM marca 
WHERE id_marca = (
    SELECT id_marca 
    FROM equipo 
    WHERE id_equipo = (
        SELECT id_equipo 
        FROM orden_servicio_has_equipo 
        WHERE nro_orden = 1
        LIMIT 1
    )
);

    Explicación pedagógica clave: Este es un reto excelente para mostrar el "anidamiento en cebolla" (múltiples niveles). 1. La consulta más interna trae el ID del equipo en la orden 1 (devuelve 1). 2. La consulta intermedia busca la marca para el equipo ID 1 (devuelve 1). 3. La consulta externa busca el nombre de la marca con ID 1 (devuelve 'Samsung').
    Para pensar: ¿Por qué agregamos LIMIT 1 en la consulta interna? Si una orden de servicio tuviera cargados dos equipos diferentes al mismo tiempo, el signo = se rompería arrojando error. El LIMIT 1 es un cinturón de seguridad escolar para garantizar que la subconsulta siga siendo estrictamente escalar.

02

Subconsultas de Lista - Resoluciones

Evaluar pertenencia en listas de valores con IN / NOT IN

Consejo de trabajo

El NOT IN con nulos es una trampa silenciosa. Probá agregar un registro de prueba en orden_servicio con el cliente en nulo y ejecutá el NOT IN sin filtrarlo: la consulta devuelve 0 resultados sin dar ningún error. Es la lógica de tres valores de SQL, y por eso conviene descartar los nulos siempre que uses NOT IN.

  • Reto 2.1

    Clientes activos (Con al menos una orden)

    Volver a la consigna
    SQL 
    SELECT nombre, apellido 
FROM cliente 
WHERE id_cliente IN (
    SELECT DISTINCT id_cliente 
    FROM orden_servicio
);

    Explicación: La subconsulta trae la columna de IDs de clientes que han abierto alguna orden (ej: 1, 2, 5). La consulta externa filtra las filas de clientes donde su ID coincida con ese conjunto. Usar DISTINCT en la consulta interna no es obligatorio para el resultado final, pero sí es una buena práctica de optimización para reducir el tamaño de la lista que SQL debe evaluar.

  • Reto 2.2

    Clientes inactivos (Sin ninguna orden asociada)

    Volver a la consigna
    SQL 
    SELECT nombre, apellido 
FROM cliente 
WHERE id_cliente NOT IN (
    SELECT DISTINCT id_cliente 
    FROM orden_servicio 
    WHERE id_cliente IS NOT NULL
);

    Explicación teórica de la protección de nulos: ¿Por qué agregamos WHERE id_cliente IS NOT NULL? Si hay una orden huérfana en la base de datos (con cliente nulo), la subconsulta generaría la lista (1, 2, 5, NULL). Al hacer NOT IN, SQL traduce la consulta como: id_cliente != 1 AND id_cliente != 2 AND id_cliente != 5 AND id_cliente != NULL. Como comparar contra NULL da "Desconocido" (UNKNOWN), toda la cadena lógica AND se destruye, haciendo que la consulta devuelva cero filas. Filtrar el nulo es obligatorio.

03

Subconsultas Correlacionadas y EXISTS - Resoluciones

Evaluar existencia cruzada fila por fila

Consejo de trabajo

Fijate dónde está el enlace de la subconsulta de EXISTS: la condición t.id_cliente = c.id_cliente usa la c de la consulta de afuera. Esa letra viaja adentro de la subconsulta en cada vuelta del motor, y por eso el resultado cambia fila por fila. El SELECT 1 está ahí porque a la base le alcanza con saber si hay al menos un registro; las columnas no las usa.

  • Reto 3.1

    Clientes con teléfono cargado (EXISTS)

    Volver a la consigna
    SQL 
    SELECT apellido, nombre 
FROM cliente AS c 
WHERE EXISTS (
    SELECT 1 
    FROM telefono AS t 
    WHERE t.id_cliente = c.id_cliente
);

    Explicación: Por cada cliente c evaluado por la consulta externa, se corre la subconsulta buscando un teléfono t asociado a su ID. Si se encuentra al menos uno, el EXISTS se vuelve TRUE y el cliente pasa a la lista final de resultados.

  • Reto 3.2

    Clientes sin correo electrónico registrado (NOT EXISTS)

    Volver a la consigna
    SQL 
    SELECT apellido, nombre 
FROM cliente AS c 
WHERE NOT EXISTS (
    SELECT 1 
    FROM email AS e 
    WHERE e.id_cliente = c.id_cliente
);

    Explicación: Funciona igual al anterior pero invertido: NOT EXISTS da TRUE únicamente si la subconsulta interna devuelve 0 filas (es decir, si el cliente evaluado no tiene ningún registro en la tabla de correos electrónicos). A diferencia de NOT IN, NOT EXISTS es inmune al problema de los valores nulos, por lo que es mucho más seguro en tablas complejas.
