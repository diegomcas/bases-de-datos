Antes de dar la clase: sobre qué datos corre esto

Todos los resultados esperados de esta guía están calculados sobre el dataset base: ElChip.sql (estructura) + poblar_elchip.sql (datos). Son 5 clientes, 3 órdenes, 5 equipos, 6 repuestos y 6 problemas. No corre sobre poblar_elchip_compendio.sql.

Un detalle de secuencia importante: los bloques 02, 03 y 04 modifican la base. Los resultados del bloque 03 y del bloque 05 suponen que los alumnos ya ejecutaron los INSERT del bloque 02. Si alguien se salteó un bloque, sus números van a diferir, y eso es esperable: conviene anticiparlo en voz alta.

Para volver al punto de partida en cualquier momento, basta con re-ejecutar los dos scripts en orden (ElChip.sql recrea el esquema desde cero).

⚠️ Errata del material original: en el PDF de origen, el desafío del aumento general de precios figura rotulado como "Desafío H", repitiendo la letra del primer desafío de INSERT. Acá se lo renombró Desafío K para respetar la secuencia H, I, J, K, L, M, N, Ñ, O, P. Si usás el PPT en pantalla, avisá del salto.
01

Lectura y Exploración - Resoluciones

Proyección, selección y ordenamiento sobre una sola tabla

Pedagogía en clase:

El Reto 1.1 esconde el concepto más valioso del bloque: se ordena por una columna que no se muestra. Casi todos los alumnos van a agregar precio_unitario al SELECT "porque si no, no puedo ordenar". Dejalos hacerlo, y después sacá la columna del SELECT dejando el ORDER BY intacto y mostrá que sigue funcionando. Ahí se entiende que SELECT y ORDER BY son etapas distintas del procesamiento.

  • Reto 1.1 Desafío A

    Repuestos con stock crítico

    Volver a la consigna
    SQL 
    SELECT nombre, stock
FROM repuesto
WHERE stock < 5
ORDER BY precio_unitario DESC;
    nombrestock
    Módulo iPhone 13 Genérico3
    Módulo Motorola Edge 302

    Explicación: el WHERE descarta las filas con stock de 5 o más (ojo: < 5 es estricto, el Módulo Samsung S21 con stock 5 no aparece). El ORDER BY precio_unitario DESC funciona aunque el precio no esté proyectado, porque el ordenamiento se aplica sobre las filas completas, antes de recortar las columnas que se muestran.

  • Reto 1.2 Desafío B

    Buscar un cliente por apellido

    Volver a la consigna
    SQL 
    SELECT apellido
FROM cliente
WHERE apellido = 'Perez';
    apellido
    Pérez

    La sorpresa didáctica: el dato está guardado como 'Pérez' con tilde, y sin embargo la consulta con 'Perez' lo encuentra. Esto pasa porque MySQL 8 usa por defecto la collation utf8mb4_0900_ai_ci: ai = accent insensitive (ignora tildes) y ci = case insensitive (ignora mayúsculas). Por eso 'perez' y 'PEREZ' también funcionan.

    Para no dejarlo como magia: aclará que esto es una propiedad de esta configuración, no de SQL en general. Con una collation _cs (case sensitive) o _bin (binaria), la misma consulta devolvería cero filas. Se puede demostrar en el momento:

    SQL — Demostración 
    -- Comparación binaria: distingue tildes y mayúsculas. Devuelve 0 filas.
SELECT apellido FROM cliente WHERE apellido = BINARY 'Perez';

-- Búsqueda parcial, útil cuando no sabemos cómo está escrito:
SELECT apellido FROM cliente WHERE apellido LIKE 'Per%';

  • Reto 1.4 Desafío D

    Catálogo de tipos de equipo

    Volver a la consigna
    SQL 
    SELECT DISTINCT tipo
FROM equipo
ORDER BY tipo ASC;
    tipo
    Celular
    Smartwatch
    Tablet

    Explicación: la tabla tiene 5 equipos, pero tres de ellos son celulares. DISTINCT colapsa las filas repetidas y deja un catálogo de 3 valores. Sin DISTINCT, "Celular" aparecería tres veces.

    Momento de diseño: aprovechá para señalar que tipo es un texto libre dentro de equipo. Si mañana alguien carga "celular" en minúscula o "Teléfono", el catálogo se ensucia. La solución normalizada sería una tabla equipo_tipo, igual que ya existe marca. Es un buen puente hacia la clase de normalización.

  • Reto 1.5 Desafío E

    Rango de mano de obra

    Volver a la consigna
    Estrategia 1 — BETWEEN
    SQL 
    SELECT descripcion, mano_obra
FROM problema
WHERE mano_obra BETWEEN 2000 AND 8000;
    Estrategia 2 — Doble comparación con AND
    SQL 
    SELECT descripcion, mano_obra
FROM problema
WHERE mano_obra >= 2000
  AND mano_obra <= 8000;
    descripcionmano_obra
    Batería agotada / Cambio de batería4500.00
    Pin de carga dañado5000.00
    Limpieza y mantenimiento preventivo3000.00
    Error de Software / Reinstalación6000.00
    Cámara principal no enfoca7500.00

    5 filas. Queda afuera únicamente "Pantalla rota" ($8500).

    Explicación: las dos consultas son equivalentes: BETWEEN a AND b es azúcar sintáctico de >= a AND <= b, con ambos extremos incluidos. Confirmalo con "Pin de carga dañado", que vale exactamente $5000, y con el hecho de que $8000 también entraría si existiera un problema con ese valor.

    Trampa a nombrar: BETWEEN 8000 AND 2000 (al revés) devuelve cero filas, no da error. El primer valor debe ser el menor.

  • Reto 1.6 Desafío F

    Órdenes todavía no entregadas

    Volver a la consigna
    Estrategia 1 — Por la fecha de entrega
    SQL 
    SELECT nro_orden, fecha_ingreso, fecha_entrega, id_orden_estado
FROM orden_servicio
WHERE fecha_entrega IS NULL;
    nro_ordenfecha_ingresofecha_entregaid_orden_estado
    12026-05-01 10:00:00NULL3
    22026-05-02 11:30:00NULL3
    32026-05-10 10:45:00NULL1

    3 filas: devuelve TODAS las órdenes de la base.

    Estrategia 2 — Por el estado de la orden
    SQL 
    -- Primero averiguamos qué id corresponde a 'Entregado':
SELECT * FROM orden_estado;   -- Entregado = 3

SELECT nro_orden, fecha_ingreso, id_orden_estado
FROM orden_servicio
WHERE id_orden_estado <> 3;

-- Versión sin números mágicos, usando una subconsulta:
SELECT nro_orden, fecha_ingreso, id_orden_estado
FROM orden_servicio
WHERE id_orden_estado <> (
    SELECT id_orden_estado FROM orden_estado WHERE nombre = 'Entregado'
);
    nro_ordenfecha_ingresoid_orden_estado
    32026-05-10 10:45:001

    1 fila: solo la orden pendiente.

    ⚠️ Este reto es el más importante del bloque y hay que dedicarle tiempo: las dos estrategias dan resultados distintos (3 filas contra 1 fila), y eso no es un error de los alumnos. Las órdenes 1 y 2 están marcadas con estado "Entregado" pero nunca se les cargó la fecha_entrega. Los datos son internamente inconsistentes.

    Cómo capitalizarlo: la respuesta correcta según el negocio es la Estrategia 2, porque el estado es el campo que el taller mantiene al día. Pero la conclusión que se llevan los alumnos es más grande que este ejercicio: cuando la misma pregunta se puede responder desde dos columnas distintas, la base tarde o temprano se va a contradecir. La solución de fondo no es elegir mejor la consulta, es que un TRIGGER (o la aplicación) complete la fecha_entrega cuando el estado pasa a "Entregado". Eso enlaza directo con el taller de Triggers.

    Error clásico a provocar: pedile a alguien que escriba WHERE fecha_entrega = NULL. Devuelve cero filas sin dar error, que es lo peligroso. NULL significa "desconocido", y comparar dos desconocidos nunca da verdadero: por eso existe IS NULL.

  • Reto 1.7 Desafío G

    Equipos de marcas puntuales

    Volver a la consigna
    Estrategia 1 — IN
    SQL 
    SELECT id_equipo, tipo, modelo, id_marca
FROM equipo
WHERE id_marca IN (1, 3, 5);
    Estrategia 2 — Cadena de OR
    SQL 
    SELECT id_equipo, tipo, modelo, id_marca
FROM equipo
WHERE id_marca = 1
   OR id_marca = 3
   OR id_marca = 5;
    id_equipotipomodeloid_marca
    1CelularGalaxy S211
    3TabletTab P113
    5SmartwatchMi Band 75

    Explicación: IN (lista) es exactamente una cadena de OR comprimida. Con tres valores la diferencia es estética; con veinte, el OR se vuelve ilegible y propenso a errores.

    El error que hay que provocar a propósito: muchos alumnos escriben WHERE id_marca = 1 OR 3 OR 5. Eso no da error de sintaxis: MySQL lo evalúa como (id_marca = 1) OR (3) OR (5), y como cualquier número distinto de cero es verdadero, devuelve la tabla entera. Es el ejemplo perfecto de por qué "no dio error" nunca significa "está bien".

    Bonus si sobra tiempo: mostrá la versión que no depende de recordar IDs, WHERE id_marca IN (SELECT id_marca FROM marca WHERE nombre IN ('Samsung','Lenovo','Xiaomi')), y anticipá que ese es el tema del taller de subconsultas.

02

Inserción de Datos - Resoluciones

Altas, valores por defecto y dependencias entre tablas

Pedagogía en clase:

Los retos 2.1 y 2.2 salen solos; el 2.3 es el que enseña. Dejá que intenten INSERT INTO orden_servicio (cliente) VALUES ('Carlos López'); y que choquen con el error. Ahí se ve, en un caso concreto, para qué sirvió todo el trabajo de normalización: la orden no guarda un nombre, guarda una referencia. Hacé que ejecuten DESCRIBE orden_servicio; y lean juntos qué columnas son NOT NULL antes de escribir nada.

  • Reto 2.1 Desafío H

    Alta de un repuesto

    Volver a la consigna
    SQL 
    INSERT INTO repuesto (nombre, stock, precio_unitario)
VALUES ('Modulo Pantalla Samsung A54', 10, 15000.00);

-- Verificación:
SELECT * FROM repuesto WHERE nombre LIKE '%A54%';

    Explicación: no escribimos id_repuesto porque es AUTO_INCREMENT: el motor le asigna el 7. Se puede confirmar en el momento con SELECT LAST_INSERT_ID();, que devuelve el ID generado por la última inserción de esta sesión.

    Detalle a mencionar: el nombre va tal como lo pidió Martín, "Modulo" sin tilde. Guardalo así a propósito: en el Reto 3.2 vamos a buscar LIKE '%Módulo%' con tilde y esta fila va a aparecer igual. Ese es el enganche.

  • Reto 2.2 Desafío I

    Alta de una marca

    Volver a la consigna
    SQL 
    INSERT INTO marca (nombre) VALUES ('LG');

SELECT LAST_INSERT_ID();   -- Devuelve 8
SELECT * FROM marca;

    Explicación: la tabla trae 7 marcas cargadas (Samsung, Apple, Lenovo, Motorola, Xiaomi, Google, Sony), así que LG queda con id_marca = 8.

    Experimento de 30 segundos: hacé que ejecuten el mismo INSERT dos veces. La segunda falla con ERROR 1062 (23000): Duplicate entry 'LG' for key 'marca.nombre_UNIQUE', porque la columna tiene un índice UNIQUE. Es la primera restricción de integridad que van a ver en acción, y prepara el terreno para el bloque 04.

  • Reto 2.3 Desafío J

    Alta de una orden de servicio

    Volver a la consigna
    Paso 1 — Averiguar los IDs
    SQL 
    SELECT id_cliente, nombre, apellido FROM cliente;  -- Carlos López = 3
SELECT * FROM orden_estado;                        -- Pendiente = 1
SELECT id_empleado, usuario FROM empleado;        -- tecnico_juan = 2
    Paso 2 — La inserción (versión directa)
    SQL 
    INSERT INTO orden_servicio (fecha_ingreso, id_empleado, id_cliente, id_orden_estado)
VALUES (NOW(), 2, 3, 1);
    Paso 2 bis — La misma inserción, sin números mágicos
    SQL 
    INSERT INTO orden_servicio (fecha_ingreso, id_empleado, id_cliente, id_orden_estado)
VALUES (
    NOW(),
    (SELECT id_empleado FROM empleado WHERE usuario = 'tecnico_juan'),
    (SELECT id_cliente FROM cliente WHERE nombre = 'Carlos' AND apellido = 'López'),
    (SELECT id_orden_estado FROM orden_estado WHERE nombre = 'Pendiente')
);

-- Verificación:
SELECT * FROM orden_servicio ORDER BY nro_orden DESC LIMIT 1;
    nro_ordenfecha_ingresofecha_entregadescuentototalid_empleadoid_clienteid_orden_estado
    4(fecha y hora de hoy)NULL0.000.00231

    Por qué hay que nombrar tantas columnas: id_empleado, id_cliente e id_orden_estado son NOT NULL y no tienen valor por defecto, así que sin ellas la fila se rechaza. En cambio descuento y total tienen DEFAULT 0.00 y fecha_entrega admite nulos: los omitimos sin problema. La orden nace sin fecha de entrega, que es justamente lo correcto.

    Sobre fecha_ingreso: la columna está declarada DEFAULT CURRENT_TIMESTAMP, así que también valdría omitirla y el motor pondría la fecha y hora actuales. Escribir NOW() explícito hace visible la intención de la consigna ("la fecha de ingreso debe ser la de hoy"), y es buena excusa para mostrar la diferencia con CURDATE(), que devuelve solo la fecha, sin hora.

    La versión con subconsultas vale oro: es más larga, sí, pero no se rompe si mañana los IDs son otros y se lee como la frase del cliente: "una orden para Carlos López, en estado Pendiente, recibida por tecnico_juan". Mostrá las dos y dejá que elijan.

    ⚠️ Error esperable: si alguien pone un id_cliente que no existe (por ejemplo, 99), obtiene ERROR 1452 (23000): Cannot add or update a child row: a foreign key constraint fails. Es el mismo mecanismo del bloque 04 pero al insertar: la base no permite una orden de un cliente inexistente.

Actualización de Datos - Resoluciones

Modificaciones masivas, selectivas y puntuales

Pedagogía en clase:

Instalá el reflejo del SELECT previo y no lo sueltes en toda la clase: toda sentencia UPDATE se escribe primero como SELECT con el mismo WHERE. Pedí que antes de ejecutar el 3.2 cada uno anote en el cuaderno cuántas filas cree que va a tocar; después comparan contra el Rows matched que informa MySQL. Los que anoten 3 (contando solo los "Módulo" con tilde) van a descubrir solos el efecto de la collation.

  • Reto 3.1 Desafío K

    Aumento general del 10%

    Volver a la consigna
    SQL 
    -- Paso 1: mirar el estado actual
SELECT id_repuesto, nombre, precio_unitario FROM repuesto;

-- Paso 2: el aumento (sin WHERE: alcanza a todas las filas, a propósito)
UPDATE repuesto
SET precio_unitario = precio_unitario * 1.10;

-- Paso 3: verificar
SELECT id_repuesto, nombre, precio_unitario FROM repuesto;
    nombreprecio anteriorprecio nuevo
    Módulo Samsung S21 Original45000.0049500.00
    Módulo iPhone 13 Genérico32000.0035200.00
    Batería iPhone 11/1212000.0013200.00
    Pin de carga Universal USB-C1500.001650.00
    Módulo Motorola Edge 3028000.0030800.00
    Batería Samsung Serie A9500.0010450.00
    Modulo Pantalla Samsung A5415000.0016500.00

    7 filas afectadas (la séptima es la que se insertó en el Reto 2.1).

    Explicación: el motor lee el precio viejo de cada fila, lo multiplica y escribe el resultado en la misma columna. Como precio_unitario es DECIMAL(10,2), el resultado se redondea a dos decimales al guardarse. Esto es relevante en importes que no son redondos: si el precio fuera 1499.99, el 10% daría 1649.989 y quedaría almacenado como 1649.99.

    ⚠️ Si en lugar del cliente de consola usan MySQL Workbench, este UPDATE sin WHERE es rechazado por el modo seguro: Error Code: 1175. You are using safe update mode.... Se destraba con SET SQL_SAFE_UPDATES = 0; o agregando un WHERE id_repuesto > 0;. Vale la pena mostrarlo: esa protección existe justamente porque el UPDATE sin WHERE es una de las formas más habituales de arruinar una base en producción.

    Aumento selectivo por nombre

    Volver a la consigna
    SQL 
    -- Paso 1: ver a quiénes va a alcanzar
SELECT id_repuesto, nombre, precio_unitario
FROM repuesto
WHERE nombre LIKE '%Módulo%';

-- Paso 2: el mismo WHERE, ahora con UPDATE

    nombreantes del 3.2después del 3.2
    Módulo Samsung S21 Original49500.0054450.00

  • Reto 3.3 Desafío M

    Corrección de un dato mal cargado

    Volver a la consigna
    SQL 
    -- Paso 1: identificar la fila
SELECT * FROM cliente WHERE id_cliente = 1;

-- Paso 2: corregir
UPDATE cliente
SET nombre = 'Juan Carlos'
WHERE id_cliente = 1;
    id_clientenombreapellido
    1Juan CarlosPérez

    Explicación: el WHERE apunta a la clave primaria, que es la forma más segura de modificar exactamente una fila. MySQL responde Rows matched: 1 Changed: 1.

    Detalle fino que suele preguntarse: si volvés a ejecutar el mismo UPDATE, MySQL informa Rows matched: 1 Changed: 0. Encontró la fila, pero el valor ya era ese y no la reescribió. "Matched" y "changed" son cosas distintas y conviene que lo sepan leer.

    Contraejemplo para cerrar el bloque: preguntá qué habría pasado con WHERE nombre = 'Juan' en lugar del ID. En esta base funcionaría por casualidad (hay un solo Juan), pero el día que entre otro cliente llamado Juan, la misma sentencia le cambia el nombre a dos personas. Los nombres no identifican; las claves primarias, sí.

04

Borrado de Datos - Resoluciones

Cuándo la base deja borrar y cuándo se planta

Pedagogía en clase:

Este bloque está diseñado para que uno funcione y el otro falle. No adelantes el final: pediles que ejecuten los dos y que ellos mismos formulen la hipótesis de por qué el segundo se niega. El error 1451 es el protagonista de la clase, no un accidente. Y remarcá el contraste con el bloque 03: un UPDATE mal apuntado se ejecuta igual y arruina datos en silencio; este DELETE, en cambio, es la base cuidándote.

  • Reto 4.1 Desafío N

    Borrar la marca recién creada

    Volver a la consigna
    SQL 
    -- Paso 1: confirmar qué vamos a borrar
SELECT * FROM marca WHERE nombre = 'LG';

-- Paso 2: borrar
DELETE FROM marca WHERE nombre = 'LG';

-- Equivalente, apuntando a la clave primaria:
-- DELETE FROM marca WHERE id_marca = 8;

    Query OK, 1 row affected.

    Por qué este sí funciona: LG se creó hace cinco minutos y ningún equipo la referencia. La fila no tiene "hijos", así que borrarla no deja nada colgado. Verificalo antes con SELECT * FROM equipo WHERE id_marca = 8;, que devuelve 0 filas.

    Nota: el AUTO_INCREMENT no retrocede. Si después insertan otra marca, va a recibir el ID 9, no el 8. Los identificadores no se reciclan, y está bien que así sea.

  • Reto 4.2 Desafío Ñ

    Borrar el cliente 1 (y entender el error)

    Volver a la consigna
    SQL 
    DELETE FROM cliente WHERE id_cliente = 1;
    Salida de MySQL 
    ERROR 1451 (23000): Cannot delete or update a parent row:
a foreign key constraint fails
(`el_chip`.`telefono`, CONSTRAINT `fk_telefono_cliente`
 FOREIGN KEY (`id_cliente`) REFERENCES `cliente` (`id_cliente`))

    Por qué falló: el cliente 1 es una fila padre. Otras tablas guardan su id_cliente como clave foránea y esas FK están declaradas ON DELETE NO ACTION (que en InnoDB se comporta como RESTRICT). Antes de borrar, el motor revisa si alguien lo referencia; como sí, aborta la operación completa. El mensaje nombra la primera restricción que encontró, no todas: la de telefono.

    Que lo demuestren ellos. Estas tres consultas muestran quiénes dependen del cliente 1:

    SQL — Diagnóstico 
    SELECT * FROM telefono        WHERE id_cliente = 1;  -- 1 fila
SELECT * FROM email           WHERE id_cliente = 1;  -- 1 fila
SELECT * FROM orden_servicio  WHERE id_cliente = 1;  -- 1 fila (la orden 1)

    La pregunta que hay que hacer: ¿qué pasaría si la base dejara borrarlo? La orden 1 quedaría a nombre del cliente 1, que ya no existe. Sería una orden fantasma: cobrada, pagada, con equipos asociados, y sin dueño. Ese estado se llama fila huérfana, y evitarlo es exactamente la razón de ser de la integridad referencial.

    Las tres salidas posibles (mostralas como decisiones de negocio, no como trucos de SQL):

    SQL — Alternativas 
    -- 1) Borrado en cascada MANUAL: primero los hijos, después el padre.
--    Funciona, pero destruye el historial comercial del taller.
DELETE FROM telefono WHERE id_cliente = 1;
DELETE FROM email    WHERE id_cliente = 1;
--    ...y todavía faltarían la orden 1, sus pagos y sus equipos asociados.

-- 2) Cambiar la política de la FK al diseñar el modelo (ON DELETE CASCADE):
--    el motor borraría los hijos solo. Cómodo y peligrosísimo en tablas
--    con historial: un DELETE se lleva puestos años de datos.

-- 3) BAJA LÓGICA (lo que hace un sistema real): no se borra, se marca.
--    Requiere una columna 'activo' o 'fecha_baja' en cliente.
--    UPDATE cliente SET activo = 0 WHERE id_cliente = 1;
    ⚠️ No dejes que "resuelvan" el reto borrando todo lo que cuelga del cliente. Si alguien lo hace, la base queda sin la orden 1 y los resultados del resto de la clase dejan de coincidir. Además, la respuesta correcta a la consigna no es lograr el borrado: es explicar por qué el motor se niega. La opción 3 (baja lógica) es la que usan los sistemas de verdad, y conviene que se la lleven anotada.
05

Navegación de Datos - Resoluciones

Paginación con LIMIT y OFFSET

Pedagogía en clase:

Dibujá la tabla completa ordenada en el pizarrón y tachá físicamente las filas que el OFFSET descarta. Es un tema que se entiende en diez segundos de forma visual y que se enreda si se explica solo con palabras. Cerrá pidiendo la fórmula general: si en el examen aparece "páginas de 20 registros, quiero la página 7", tienen que poder responder LIMIT 20 OFFSET 120 sin dudar.

    -- Página 2 (tamaño de página = 2): salteo 2, traigo 2
SELECT * FROM repuesto
ORDER BY nombre ASC
LIMIT 2 OFFSET 2;

-- Página 3: salteo 4, traigo 2
SELECT * FROM repuesto
ORDER BY nombre ASC
LIMIT 2 OFFSET 4;

-- Sintaxis abreviada de MySQL (¡el orden se invierte!):
-- LIMIT 2, 2  →  saltea 2, trae 2   (equivale a LIMIT 2 OFFSET 2)
-- LIMIT 4, 2  →  saltea 4, trae 2   (equivale a LIMIT 2 OFFSET 4)
    páginafilas devueltas
    1 (OFFSET 0)Batería iPhone 11/12 · Batería Samsung Serie A
    2 (OFFSET 2)Módulo iPhone 13 Genérico · Módulo Motorola Edge 30
    3 (OFFSET 4)Modulo Pantalla Samsung A54 · Módulo Samsung S21 Original
    4 (OFFSET 6)Pin de carga Universal USB-C

    Con los 7 repuestos (6 originales + el del Reto 2.1). Si el grupo no hizo el INSERT del bloque 02, son 6 repuestos y la última página trae "Módulo Samsung S21 Original" y "Pin de carga Universal USB-C".

    La fórmula: OFFSET = (número_de_página − 1) × tamaño_de_página. Con páginas de 2: página 1 → offset 0, página 2 → offset 2, página 3 → offset 4. Es la cuenta que hace cualquier framework web por detrás cuando armás una tabla paginada.

    Sobre la inconsistencia del PPT original: la diapositiva pide "los siguientes 2 (del 3 al 4)" pero el ejemplo de sintaxis muestra LIMIT 5 OFFSET 5. No es un error a corregir en silencio: usalo. Preguntá qué devuelve LIMIT 5 OFFSET 5 sobre esta tabla y van a ver que trae solo 2 filas (la 6.ª y la 7.ª), porque no hay más registros. Que la última página venga incompleta es normal y hay que preverlo.

    Por qué el orden de "Modulo Pantalla" sorprende: aparece entre "Módulo Motorola" y "Módulo Samsung" aunque esté escrito sin tilde. Otra vez la collation ai_ci: para ordenar, MySQL trata "Modulo" y "Módulo" como iguales y desempata por la palabra siguiente (iPhone, Motorola, Pantalla, Samsung).

    ⚠️ Sin ORDER BY no hay paginación: si sacás el ORDER BY, MySQL puede devolver las filas en cualquier orden y no está obligado a mantener el mismo entre una consulta y la siguiente. La "página 2" podría repetir filas de la "página 1" y saltearse otras. ORDER BY no es un adorno acá: es lo que hace que la paginación signifique algo.
