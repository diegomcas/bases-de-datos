Introducción

En informática, un diagrama es una representación gráfica que permite modelar, simplificar y comunicar estructuras, procesos o sistemas complejos. Su objetivo principal es facilitar la comprensión y el análisis mediante elementos visuales estandarizados, reduciendo ambigüedades y permitiendo que distintos actores (analistas, desarrolladores y clientes) compartan un mismo entendimiento del problema.

Dentro de este contexto, el Diagrama Entidad-Relación (DER) es una herramienta de modelado conceptual utilizada en bases de datos para representar la estructura de la información de un sistema. A través de entidades, atributos y relaciones, el DER permite abstraer la realidad del dominio del problema y definir cómo se organizan y vinculan los datos, constituyendo el punto de partida para el diseño lógico y la implementación de la base de datos.

Objetivo de la Clase: Dominar el Diagrama Entidad-Relación (DER) como herramienta para analizar, abstraer y representar formalmente la realidad, garantizando una base sólida para el diseño lógico de bases de datos.

¿Qué estamos modelando?

Un sistema de información representa una porción de la realidad que se desea gestionar.

El proceso de modelado implica:

  • Observar el mundo real
  • Seleccionar qué información es relevante
  • Representarla de forma estructurada

Este proceso se denomina abstracción.

No todo lo real se modela: el diseñador decide qué incluir según los objetivos del sistema.

Entidades y Atributos

Entidades

Son objetos del mundo real (concretos o abstractos) sobre los cuales se desea almacenar información.

Tipos:

  • Entidades Fuertes:
  • Existen de manera independiente dentro del sistema.
  • Ej: ALUMNO, CLIENTE, PRODUCTO.
  • Entidades Débiles:
  • Dependen de otra entidad para existir.
  • Ej: CUOTA depende de ALUMNO.
  • Interpretación conceptual:
  • No tienen sentido por sí solas.
  • Representan partes o detalles de otra entidad.

Atributos

Son propiedades que describen a una entidad.

Tipos:

  • Simples (atómicos):
  • No se pueden descomponer.
  • Ej: Nombre
  • Compuestos:
  • Se dividen en subatributos.
  • Ej: Dirección → Calle, Número, Ciudad.
  • Multivaluados:
  • Admiten múltiples valores.
  • Ej: Teléfono.

Relaciones

Las relaciones representan asociaciones entre entidades.

Ejemplo:

ALUMNO — CURSA — MATERIA

Las relaciones pueden:

  • Vincular dos o más entidades
  • Tener atributos propios

Ejemplo:

INSCRIPCIÓN → FechaInscripción

En algunos casos, cuando una relación tiene atributos propios, puede ser necesario analizar si debe modelarse como una estructura independiente en etapas posteriores.

Reglas del Negocio: Cardinalidad y Participación

Las relaciones entre entidades están determinadas por reglas del negocio.

Estas reglas se expresan mediante:

  • Cardinalidad
  • Participación

Cardinalidad (cuántos)

Indica el número máximo de instancias de una entidad que pueden relacionarse con otra.

  • 1:1 → Un DIRECTOR dirige una ESCUELA
  • 1:N → Un CLIENTE realiza muchos PEDIDOS
  • N:M → Muchos ALUMNOS cursan muchas MATERIAS

Participación (obligatoriedad)

Indica si una entidad debe o no participar en una relación

  • Total (obligatoria): Todas las instancias participan
  • Parcial (opcional): Algunas instancias pueden no participar

Notación (mín, máx)

Una forma más precisa de representar estas reglas es mediante pares (mín, máx):

  • (0,1) → opcional, máximo uno
  • (1,1) → obligatorio, uno
  • (0,N) → opcional, muchos
  • (1,N) → obligatorio, muchos

La notación (mín, máx) integra cardinalidad y participación en una sola expresión.

Problema de Identificación: Claves

En un sistema real puede ocurrir:

Dos entidades distintas con los mismos atributos visibles.

Ejemplo: Dos alumnos con el mismo nombre.

Esto plantea un problema:

¿Cómo identificamos de forma única cada instancia?

A. Tipos de Claves

  • Superclave: Conjunto de atributos que permite identificar unívocamente una entidad
  • Clave Candidata: Superclave mínima (sin atributos redundantes)
  • Clave Primaria (PK): Clave elegida como identificador principal

Debe cumplir:

  • Ser única
  • No ser nula
  • Ser estable en el tiempo

Claves Compuestas

Una clave puede estar formada por más de un atributo.

Ejemplo: INSCRIPCIÓN → (id_alumno, id_materia)

Este tipo de clave surge cuando una relación entre entidades requiere una identificación propia.

Clave Natural vs Subrogada

  • Clave Natural: Proviene del mundo real. Ej: DNI
  • Clave Subrogada: Generada por el sistema. Ej: id_alumno

En sistemas reales se suelen preferir claves subrogadas por su estabilidad.

6. Entidades Débiles (Formalización)

Las entidades débiles presentan un problema de identificación: No pueden identificarse por sí solas.

Por eso:

  • Se identifican utilizando:
  • La clave de la entidad fuerte
  • Un atributo propio (clave parcial)

Ejemplo: CUOTA → (id_alumno, número_cuota)

Esta identificación se establece mediante una relación identificadora.

Atributos Derivados

Algunos atributos pueden obtenerse a partir de otros.

Ejemplo:

  • Edad a partir de FechaNacimiento

Esto plantea una decisión de diseño:

  • Almacenar el valor
  • Calcularlo cuando se necesite

La elección depende de:

  • Frecuencia de uso
  • Costos de cálculo
  • Consistencia de los datos

Relaciones con Atributos y Decisiones de Modelado

Cuando una relación posee atributos propios, puede comportarse conceptualmente como una entidad.

Ejemplo:INSCRIPCIÓN:

  • relaciona ALUMNO y MATERIA
  • tiene atributo FechaInscripción

En estos casos, el diseñador debe decidir:

  • Mantenerla como relación
  • modelarla como una entidad independiente

Esta decisión impacta directamente en el diseño posterior.

Jerarquías (Generalización / Especialización)

Permiten representar relaciones de tipo “es un”.

Ejemplo:

  • EMPLEADO
  • DOCENTE
  • ADMINISTRATIVO

Tipos:

  • Total / Parcial: Todas o algunas instancias pertenecen a una subclase
  • Disjunta / Superpuesta: Una instancia pertenece a una o varias subclases

Metodología de Modelado

Proceso recomendado:

  1. Identificar entidades (sustantivos)
  2. Identificar relaciones (verbos)
  3. Definir cardinalidades
  4. Definir participación
  5. Asignar atributos
  6. Definir claves
  7. Validar con reglas del negocio

Este proceso es iterativo: el modelo se ajusta a medida que se comprende mejor el dominio.

Preguntas Clave al Cliente

  • ¿Puede existir X sin Y?
  • ¿Cuántos X pueden relacionarse con Y?
  • ¿Qué identifica de forma única a X?
  • ¿Este dato puede tener múltiples valores?
  • ¿Este dato se puede calcular?

Empleados que trabajan

Decisión de abstracción

Abstracción: La abstracción es el proceso mediante el cual se seleccionan y representan únicamente los aspectos relevantes de un sistema, ignorando los detalles innecesarios para el objetivo que se persigue.

En informática, la abstracción permite simplificar la complejidad del mundo real para poder modelarlo, analizarlo y resolver problemas de manera más eficiente.

Se incluyen:

  • CLIENTE
  • ORDEN_REPARACION
  • EQUIPO
  • REPARACION
  • REPUESTO

No se incluyen:

  • proveedores
  • facturación detallada
  • caja diaria

ENTIDADES

Una entidad es un objeto del mundo real con existencia independiente.

  • Ejemplos:
  • CLIENTE → persona que deja equipos
  • EQUIPO → celular, tablet, smartwatch
  • ORDEN_REPARACION → registro del ingreso
  • REPARACION → trabajo realizado
  • REPUESTO → componente utilizado

ATRIBUTOS

Los atributos describen características de las entidades.

CLIENTE

  • nombre
  • teléfono
  • DNI (clave candidata)

EQUIPO

  • tipo
  • marca
  • modelo
  • número de serie (clave candidata)

ORDEN_REPARACION

  • fecha_ingreso
  • estado
  • fecha_retiro

Tipos de atributos

Simples

  • nombre
  • estado

Compuestos

  • dirección (calle, número, ciudad)

Multivaluados

  • teléfono (un cliente puede tener varios)

Derivados

  • precio total de reparación

RELACIONES

Las relaciones vinculan entidades.

  • CLIENTE — DEJA — ORDEN
  • ORDEN — INCLUYE — EQUIPO
  • REPARACION — UTILIZA — REPUESTO

CARDINALIDAD

Define cuántas ocurrencias participan en una relación.

1:N

Un cliente puede tener muchas órdenesCada orden pertenece a un cliente

CLIENTE (0,N) — ORDEN (1,1)

N:M

Una reparación puede usar varios repuestosUn repuesto puede usarse en muchas reparaciones

REPARACION (N) — REPUESTO (M)

PARTICIPACIÓN

Indica si una entidad participa obligatoriamente en una relación.

  • Una orden debe tener cliente → participación total
  • Un cliente puede no tener órdenes → participación parcial

CLAVES

Permiten identificar de forma única una entidad.

Clave primaria
  • id_cliente
  • id_orden
Claves candidatas
  • DNI (cliente)
  • número de serie (equipo)

ENTIDADES DÉBILES

Son entidades que dependen de otra para existir.

DIRECCIÓN

  • No existe sin CLIENTE
  • Se identifica con:
  • id_cliente + datos de dirección

RELACIONES CON ATRIBUTOS

Algunas relaciones tienen información propia.

REPARACION — UTILIZA — REPUESTO

Atributo:

  • cantidad

No pertenece ni a reparación ni a repuesto, sino a la relación

ATRIBUTOS DERIVADOS

Se calculan a partir de otros datos.

Precio total:

  • suma de mano de obra + repuestos
  • descuento si es efectivo

No es necesario almacenarlo

11. DECISIONES DE MODELADO

El diseño implica tomar decisiones.

  • ¿REPARACION es entidad o relación?
  • Se modela como entidad
  • ¿Una orden puede tener varios equipos?
  • Sí → relación ORDEN–EQUIPO
  • ¿Cómo modelar repuestos?
  • Con una relación N:M

ERRORES COMUNES

  • Duplicar clientes por no usar DNI
  • No separar ORDEN y REPARACION
  • No modelar la relación N:M con repuestos
  • No registrar cantidad de repuestos

METODOLOGÍA DE MODELADO

Paso 1: identificar sustantivos

cliente, equipo, reparación, repuesto

Paso 2: identificar verbos

deja, incluye, utiliza

Paso 3: definir relaciones

CLIENTE — DEJA — ORDEN

Paso 4: definir cardinalidades
Paso 5: validar con reglas del negocio
