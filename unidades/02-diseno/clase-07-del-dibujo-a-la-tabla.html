Objetivo de la Clase

Aprender a transformar un modelo conceptual (Diagrama Entidad-Relación) en un modelo lógico (Esquema Relacional o de Tablas), aplicando las reglas de normalización implícita y propagación de claves.


Introducción: ¿Por qué transformar?

El DER nos permite entender el problema y comunicarnos con el cliente. Sin embargo, los sistemas gestores de bases de datos (SGBD) trabajan con:

  • Tablas
  • Filas (registros)
  • Columnas (atributos)

Por eso necesitamos traducir el DER al modelo relacional.

Este proceso se llama mapeo al modelo relacional y puede expresarse en un conjunto definido de reglas que se desarrollarán en este documento.

Idea clave

Antes de ver las reglas, anotemos una idea una idea central:

En el modelo relacional, las relaciones se representan mediante claves foráneas (FK)

Reglas de transformación (notación clara y consistente)

Convenciones que vamos a utilizar para evitar confusión, usamos siempre esta notación:

  • Entidades: CLIENTE, ORDEN -> Se convierte en -> Tablas: cliente, orden_servicio
  • PK: subrayada o indicada como (PK) (Preferentemente especificada como PK)
  • FK: indicada como (FK)
  • Cardinalidad:
  • = uno
  • (N) = muchos
  • Ejemplo: A (1) ───── (N) B

Regla 1: Entidades fuertes → Tablas

DER: CLIENTE <-> Relacional: cliente(id_cliente (PK), nombre, …, apellido, email)

  • Cada entidad genera una tabla
  • Su identificador se convierte en PK

Regla 2: Relaciones 1:N → Clave foránea

DER: CLIENTE (1) ───── (N) EQUIPO

Regla: La PK del lado (1) se agrega como FK en la tabla del lado (N)

Relacional: equipo(id_equipo (PK), ..., id_cliente (FK))

  • No se crea tabla nueva
  • La FK siempre queda del lado “muchos”

Forma de pensarlo: “Cada equipo pertenece a un cliente → el equipo guarda el id del cliente”

Regla 3: Relaciones N:M → Tabla intermedia

DER: ORDEN (N) ───── (M) EQUIPO

Regla: Se crea una nueva tabla que representa la relación

Relacional: orden_equipo (nro_orden (PK)(FK), id_equipo (PK)(FK))

  • Se crea una tabla nueva
  • La PK es compuesta por las PK de las entidades que se relacionan
  • Cada campo de la relación es también FK

Forma de pensarlo: “La relación pasa a ser una entidad”

Regla 4: Entidades débiles

DER: FACTURA (1) ───── (N) ITEM_FACTURA

Regla: La entidad débil usa una PK compuesta

Relacional: item_factura(nro_factura (PK)(FK), nro_item (PK), cantidad)

  • Depende de otra entidad
  • No tiene identidad completa por sí sola

Regla 5: Atributos especiales

Atributo compuesto

DER: direccion = (calle, numero)

Relacional: cliente(..., calle, numero)

Atributo multivaluado

DER: CLIENTE → telefono {multiple}

Relacional: cliente_telefono(id_cliente (FK), telefono)

Atributo derivado

DER: edad (derivado de fecha_nacimiento)

Relacional: NO se almacena

Caso práctico: “El Chip”

Aplicamos las reglas paso a paso.

Paso 1: Entidades → Tablas

Entidad Tabla PK
CLIENTE cliente id_cliente
EQUIPO equipo id_equipo
EMPLEADO empleado id_empleado
ORDEN orden_servicio nro_orden
REPUESTO repuesto id_repuesto
PROBLEMA problema id_problema

Paso 2: Relaciones 1:N

CLIENTE (1) —— (N) EQUIPO

EMPLEADO (1) —— (N) ORDEN

Paso 3: Relaciones N:M

ORDEN —— EQUIPO

ORDEN / EQUIPO —— PROBLEMA

PROBLEMA —— REPUESTO

El Esquema Final (Diccionario de Datos)

  • clientes (id_cliente, nombre, apellido, telefono, email)
  • equipos (id_equipo, tipo, marca, modelo, nro_serie, id_cliente)
  • empleados (id_empleado, usuario, password, rol)
  • ordenes_servicio (nro_orden, fecha_ingreso, fecha_entrega, estado, mano_obra, metodo_pago, descuento, total, id_equipo, id_empleado)
  • repuestos (id_repuesto, nombre, stock, precio_unitario)
  • problemas (id_problema, descripcion)
  • ordenes_repuestos (nro_orden, id_repuesto, cantidad)
  • ordenes_problemas (nro_orden, id_problema)
